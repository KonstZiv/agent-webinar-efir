## 1. Що ви зберете і як читати

Результат — сайт реєстрації на вебінар:

- лендінг з описом вебінару і формою реєстрації: згода, захист від ботів;
- лист-запрошення з подією для календаря і посиланням для відписки;
- Telegram-бот: прив'язує Telegram до реєстрації, перевіряє підписку на канал і видає матеріали;
- два лічильники, що оновлюються самі: «зареєструвались» і «підключили Telegram»;
- статистика і список учасників у CSV для організатора;
- два середовища в хмарі: тестове (staging) і робоче (продакшн).

Стек: Python, FastAPI, PostgreSQL, SQLAlchemy і Alembic, Jinja2 і htmx, pytest, ruff, mypy; хостинг — Railway, пошта — Resend. Стек можна замінити: процес від цього не змінюється.

Шлях:

1. **Опис і тексти** — що за сайт, для кого, що на ньому написано.
2. **Правила для агентів** — файл, який агент читає першим у кожній сесії.
3. **Специфікація** — що будуємо і чого свідомо не робимо.
4. **Зрізи** — кожна функція від сторінки до бази окремою задачею. Кожен зріз проходить один і той самий цикл: постановка → план → тести → код → гейти → рецензія.
5. **Розгортання** — staging після кожного зрізу, продакшн — рішенням людини.

Як читати:

- розділи 2–3 — до першого рядка коду;
- розділ 4 — у порядку карток, одна картка — одна нова сесія агента;
- розділи 5–7 — довідка, до якої повертаються на кожному зрізі;
- постановки в блоках коду копіюються агентові як є; назви файлів, адрес і чисел замінюються на свої.

Скільки це триває: підготовка — близько чотирьох годин активної роботи; один зріз коду — година-дві разом із планом, рецензією і перевіркою. Сам код після погодженого плану агент пише за 10–25 хвилин. Решта часу — читання плану, рецензія і перевірка: саме вони відрізняють продакшн-якість від галюцинацій.

Докладно: лекції 1–3 курсу — як думає кодинг-агент, мова постановок, один процес для трьох агентів.

## 2. Підготовка

Облікові записи, домени і ключі готує людина, і заздалегідь: підтвердження домену, видача сертифіката чи перевірка акаунта тривають від хвилин до днів, і прискорити їх неможливо. Поки пишеться код, ніщо не реєструється і не підтверджується.

Імена в прикладах умовні: домен `example.com`, адреси `app` (продакшн) і `app-next` (staging), поштовий піддомен `mail`.

### Облікові записи

| Сервіс | Навіщо | Що створити |
| :-- | :-- | :-- |
| GitHub | код, автоматичні перевірки, задачі для агента | приватний репозиторій; застосунок кодинг-агента і застосунок хостингу з доступом саме до цього репозиторію |
| Railway | тут працюють сайт і база | два проєкти — продакшн і staging; у кожному вебсервіс і PostgreSQL; власні домени |
| Домен і DNS (у прикладі — Cloudflare) | адреси сайту; підтвердження пошти | записи CNAME і TXT, які називає хостинг; режим «лише DNS», якщо зона обслуговує й інші сайти |
| Resend | листи | поштовий піддомен із записами SPF, DKIM і DMARC; ключ на кожне середовище — лише надсилання, лише свій домен |
| Telegram | канал для підписників; бот пов'язує реєстрацію з підпискою | публічний канал; два боти через @BotFather — основний і тестовий; основний — адміністратор каналу з мінімальними правами |
| Cloudflare Turnstile | відсіює ботів на формі | віджет для адрес продакшну; для staging — офіційні тестові ключі з документації |
| Google Analytics 4 — за бажанням | шлях відвідувача: перегляд → реєстрація | два ресурси — основний і тестовий; ключові події, створені наперед |
| Кодинг-агент | пише код за постановками | підписка; ліміти і день їх скидання |
| Локальне оточення | тут працюють агент і перевірки | Python, uv, git, GitHub CLI, CLI хостингу, Docker для локальної бази |

### Правило секретів

- Є менеджер паролів. Кожен ключ і токен потрапляє туди одразу після створення: частину значень сервіс показує лише раз.
- Кожне середовище має свій набір ключів: продакшн і staging не мають жодного спільного секрету.
- Секрети для GitHub Actions — у секретах репозиторію (Settings → Secrets and variables → Actions), а не у файлах.
- Локально — файл `.env` поза git (рядок у `.gitignore`), закритий для агента правилами дозволів, а не лише домовленістю. Перелік змінних без значень — `docs/env.example` у репозиторії.
- Секрети не потрапляють у чат з агентом, у репозиторій, на знімки і в запис екрана. У документах — лише назва секрету і місце зберігання.

Секрет у терміналі — без показу на екрані й в історії команд. Значення копіюється з менеджера паролів у буфер обміну, команди виконуються по одній:

```
KEY="$(pbpaste)"
echo "довжина: ${#KEY}, початок: ${KEY:0:3}"
curl -s "https://api.telegram.org/bot${KEY}/getMe"
unset KEY
```

У Linux замість `pbpaste` — `wl-paste` або `xclip -selection clipboard -o`.

### Чек-лист готовності

Кожен пункт — перевірка з відповіддю «так» або «ні».

- Кожна адреса відкривається по HTTPS: `curl -sSI https://app.example.com/` відповідає `HTTP/2 200`.
- Домен пошти має стан Verified; у заголовках тестового листа — `spf=pass`, `dkim=pass`, `dmarc=pass`.
- Метод `getMe` успішний для обох ботів; `getChatMember` показує основного бота адміністратором каналу.
- Команди `gh auth status` і `railway whoami` успішні.
- Пошук у теці проєкту не знаходить жодного значення секрету.

### Пастки, знайдені на практиці

1. Вхід на хостинг через GitHub не дає хостингу доступу до репозиторіїв: потрібен окремий застосунок GitHub із доступом до конкретного репозиторію.
2. Автоналаштування DNS від хостингу може замінити ручні записи записом у режимі проксі. Якщо потрібен режим «лише DNS», записи додаються вручну.
3. Безкоштовний тариф поштового сервісу має добовий ліміт на весь обліковий запис. Тариф обирається за найбільшою розсилкою, а не за середнім днем.
4. Ключ сайту у віджеті захисту форми публічний і нічого не підтверджує. Захищає лише перевірка токена на сервері секретним ключем.
5. Бот-адміністратор каналу має право обмежувати учасників, навіть коли всі перемикачі вимкнено. Токен бота — повноцінний секрет.
6. Панелі сервісів змінюються швидше за документацію і за знання мовної моделі: назви кнопок звіряються з екраном.
7. Підписка кодинг-агента має вікна лімітів — п'ятигодинне і тижневе. Довга робота в останню добу тижня може зупинитись на півдорозі.

Докладно: лекція 3 — вибір і налаштування агента; лекція 4 — секрети і правила дозволів.

## 3. Шаблони

### Шаблон проєкту — фундамент без бізнес-коду

Агент на порожньому місці щоразу вигадує структуру наново. Шаблон фіксує її один раз, і всі задачі лише додають файли до відомих місць.

Що в шаблоні:

- структура коду: `core` — сутності, сценарії і порти; `adapters` — база, вебмаршрути, зовнішні сервіси;
- фабрика застосунку і налаштування зі змінних середовища;
- `/healthz` для хостингу, сторінка політики приватності, банер cookie;
- Alembic для міграцій, Docker Compose для локальної бази;
- pytest із запобіжником мережі: тести не ходять в інтернет;
- гейти: ruff, mypy, pre-commit, CI у GitHub Actions з PostgreSQL;
- `Procfile` для хостингу;
- файл правил агента з порядком роботи і три шаблони курсу в `docs/templates/`;
- workflow, через які агент працює в GitHub: задачі з Issue і рецензія pull request.

Чого в шаблоні немає: моделі даних, форм, листів, бота. Це додають зрізи.

Посилання на шаблон з'явиться у версії 2 інструкції разом із відкритим репозиторієм. Поки його немає, шаблон можна зібрати першою задачею агентові:

```
## Goal
Шаблон FastAPI-проєкту без бізнес-логіки, на якому наступні задачі лише додають файли.

## Context
Склад — перелік нижче. Стек: Python, uv, FastAPI, SQLAlchemy і Alembic, PostgreSQL,
Jinja2, pydantic-settings, httpx, pytest, ruff, mypy, pre-commit, GitHub Actions.

## Constraints
Структура: src/app/core — сутності, сценарії, порти (Protocol); src/app/adapters —
реалізації портів і вебмаршрути. Ядро не імпортує FastAPI, SQLAlchemy і HTTP-клієнтів.
Застосунок збирається фабрикою, глобального стану немає.
Склад: налаштування зі змінних середовища; /healthz; сторінка політики приватності;
Alembic; compose.yaml для локальної бази; запобіжник мережі в тестах;
CI з PostgreSQL; pre-commit; Procfile; docs/env.example без значень.
Жодної предметної логіки.

## Done when
- uv run pytest, uv run ruff check ., uv run mypy src — зелені;
- застосунок запускається локально, /healthz відповідає 200;
- CI зелений на першому push.
```

### Три шаблони курсу

**Задача.** Чотири розділи — мета, контекст, обмеження, критерії готовності:

```
## Goal (мета)
Одне-два речення: що має з'явитися або змінитися в результаті.

## Context (контекст)
Що агенту треба знати: посилання на конкретні файли і зразки
(не переказ!), наявні домовленості, суміжний код.

## Constraints (обмеження)
Що фіксовано: стек і версії, стиль, що НЕ чіпати,
що заборонено (наприклад, сторонні пакети).

## Done when (критерії готовності)
Перелік перевірних тверджень. Кожне — з відповіддю «так/ні»:
команда, яка має відпрацювати; поведінка, яку можна побачити;
тест, який має пройти.
```

- Мета відповідає на «що», а не «як»: спосіб агент запропонує в плані.
- Контекст — посилання, а не переказ: агент прочитає файл сам, і точніше.
- Обмеження — лише реальні і за метою, а не за механізмом. Інакше агент виконує букву обмеження складним обхідним шляхом.
- Критерії готовності — головний розділ. «Код працює» — неперевірне; «команда друкує три показники без трейсбека» — перевірне.
- Розмита задача ділиться на кілька задач за тим самим шаблоном.

**Специфікація** — «конституція» проєкту: рішення, які не переглядаються між задачами.

```
# Специфікація: назва застосунку

## Призначення
Два-три речення: для кого застосунок і яку потребу закриває.

## Незмінні рішення
Стек і версії; мова інтерфейсу; спосіб зберігання даних;
архітектурні межі (що є, чого свідомо немає).

## Модель даних
Сутності з полями і зв'язками — коротко, таблицею або списком.

## Функціональні межі
Що застосунок робить і що НЕ робить (свідомо відкладене).

## Критерії якості
Перевірки, які мають проходити завжди (команди);
правила, що діють на кожну задачу.

## Журнал змін специфікації
Дата → що змінено → чому.
```

Задача не суперечить специфікації. Якщо мусить — спершу змінюється специфікація, із записом у журнал.

**Чек-лист рев'ю** — порядок від дешевих перевірок до дорогих:

1. Відповідність задачі: зроблено те, що просили, і нічого понад те; тести не редагувались без дозволу.
2. Правдоподібність без перевірки: викликані функції й пакети справді існують; числа і формати перевірені прикладом.
3. Помилкові шляхи: порожній вхід, недоступна база, винятки не проковтнуті мовчки.
4. Дані і стан: зміни там, де очікувались, і ніде більше; транзакції для складених операцій.
5. Безпека: секретів у коді немає; вхід користувача не потрапляє в SQL і команди без параметризації; журнали без персональних даних.
6. Простота: рішення не складніше за задачу, немає дублювання.

Формат знахідки: `файл:рядок — що не так — чому це проблема`. Знахідки віддаються агентові однією задачею на виправлення.

Докладно: лекція 2 — шаблон задачі; лекція 5 — специфікація; лекція 9 — чек-лист рев'ю.

## 4. Картки задач за зрізами

Як працювати з кожною карткою:

1. Нова сесія агента: правила проєкту, специфікація і документи мають бути достатніми, щоб працювати без історії попередніх розмов.
2. Режим планування. План читається повністю і лише потім погоджується. Якщо агент пропонує вибір кнопками — спершу прочитати план.
3. Тести першими, далі код, далі гейти — агент запускає їх сам і завершує роботу лише на зелених.
4. Підсумок агента: що змінено, коміти, результат гейтів, розбіжності, відкриті запитання.
5. Рецензія в чистій сесії (розділ 6), виправлення, перевірка на staging.

Великі зрізи мають у постановці додатковий розділ «Що входить»: перелік, де кожен пункт перевіряється окремо.

### Картка 1. Бриф і тексти

Інструмент — чат або асистент із доступом до теки; підключається лише тека з фактами. Перед запуском людина пише два файли фактів: `docs/webinar.md` — дата, час, ведучий, формат; `docs/course.md` — факти про курс чи продукт, на який веде сайт.

```
## Goal
Бриф сайту реєстрації на вебінар і готові тексти: сторінка, лист після реєстрації,
повідомлення бота.

## Context
Ідея: сайт описує вебінар, реєструє на нього, а за підключення Telegram
видає матеріали. Факти про вебінар — docs/webinar.md, про курс — docs/course.md.
Спершу прочитай факти і постав до трьох уточнювальних запитань.

## Constraints
Українська мова, звертання на «ви». Одна сторінка, один заклик до дії.
Жодного твердження, якого немає в docs/webinar.md, docs/course.md або у відповідях.
Заголовок — до 80 символів, підзаголовок — одне речення.
Тексти згоди і політики приватності не пишуться: їх готує організатор окремо.
Результат — лише нові файли docs/brief.md і docs/copy.md.

## Done when
- docs/brief.md: аудиторія, обіцянка, блоки сторінки, заклик до дії — до однієї сторінки;
- docs/copy.md: тексти кожного блоку сторінки до ефіру і після нього, форма,
  екран успіху, лист, повідомлення бота — кожен у своєму нумерованому розділі;
- коротко в сесії — на яких рядках фактів стоїть кожне твердження.
```

Навіщо кожен пункт:

- **Запитання перед текстом** — агент не вгадує аудиторію і тон, а питає.
- **Жодного твердження поза фактами** — головний захист від вигаданих дат, цін і обіцянок.
- **Нумеровані розділи `copy.md`** — на них посилаються зрізи, а тест-оракул звіряє з ними сторінки (розділ 5).
- **Без юридичних текстів** — згода і політика приватності не доручаються агентові без перевірки людиною.
- **Звідки кожне твердження** — людина перевіряє тексти за хвилини, а не перечитує факти.

Докладно: лекція 2.

### Картка 2. Правила проєкту

Файл, який агент читає на початку кожної сесії: у Claude Code — `CLAUDE.md`, у Codex і Antigravity — `AGENTS.md` (розділ 8). Якщо проєкт стартує з шаблону, файл уже є — задача його доповнює.

```
## Goal
Файл правил проєкту CLAUDE.md: що агент має знати на початку кожної сесії.

## Context
Бриф — docs/brief.md. Шаблони — docs/templates/. Структура коду і команди —
pyproject.toml, compose.yaml, .github/workflows/ci.yml.

## Constraints
До 150 рядків, списками. Розділи: порядок роботи; стек; команди (тести, лінтер,
типи, запуск, міграції); межі коду; зрізи — де лежить код зрізу і що спільне;
тексти — лише з docs/, не дописуються; секрети і дані; розгортання; правила рецензії.
Лише правила, які можна виконати або перевірити; без загальних побажань.
Змінюється лише CLAUDE.md.

## Done when
CLAUDE.md записано; у сесії — три правила, які найчастіше захищатимуть від помилок.
```

Розділ «Порядок роботи» варто взяти дослівно:

```
- Кожна задача приходить постановкою у файлі (Goal / Context / Constraints / Done when).
  Виконується лише те, що в ній названо; обсяг не розширюється.
- Перед кодом — план у режимі планування; код пишеться після погодження плану.
- Тести пишуться першими.
- Розбіжність між постановкою, специфікацією і реальністю — зупинка і повідомлення
  людині. Постановку і специфікацію самостійно не «виправляти».
- Робота завершується лише на зелених гейтах і підсумком: що змінено, коміти,
  результат гейтів, розбіжності, відкриті запитання.
- .env агентові закритий правилами дозволів; секрети не друкуються;
  команд розгортання агент не виконує.
```

Навіщо:

- **Один файл на всі сесії** — правила не повторюються в кожній постановці і не губляться між сесіями.
- **Лише перевірні правила** — «пиши якісний код» нічого не змінює; «ядро не імпортує фреймворків» перевіряє тест.
- **Зупинка на розбіжності** — агент, який «виправляє» постановку сам, тихо змінює те, що погодила людина.
- **Короткий файл** — він займає контекст у кожній сесії; довгі правила виконуються гірше.

Людина читає файл повністю: він діє на кожну наступну сесію.

Докладно: лекція 4.

### Картка 3. Специфікація

```
## Goal
Специфікація сайту — docs/spec.md: що будуємо і в яких межах.

## Context
Бриф — docs/brief.md, тексти — docs/copy.md. Шаблон — docs/templates/spec-template.md.
Фундамент уже є в репозиторії: CLAUDE.md описує, як влаштовано код.

Одна-дві сторінки за структурою шаблону. У функціональних межах — маршрути сайту

«Чого не робимо» — так само важливо, як «що робимо».
Лише docs/spec.md; код і інші документи не змінюються.

## Done when
docs/spec.md записано; коротко в сесії — три головні рішення специфікації
```

Навіщо:

- **Маршрути за зрізами** — це межі файлів: зрізи не перетинаються і можуть писатися паралельно.

- **Запитання, на які бракує відповіді** — дірки виявляються до коду, а не в коді.
- **Лише один файл** — специфікація не стає приводом переписати все інше.

Специфікація визначає код, тому проходить рецензію в чистій сесії так само, як код (розділ 6). Людина читає її повністю.

### Картка 4. Фундамент

```
## Goal
Шаблон проєкту стає фундаментом сайту — спільною основою, на яку зрізи лише
додають свої файли:
- модель даних і міграції для всіх зрізів одразу;
- налаштування всіх зрізів зі змінних середовища; docs/env.example без значень;

Фундамент без бізнес-логіки: форми, листа, бота, лічильників тут немає —

Ядро не імпортує FastAPI, SQLAlchemy і HTTP-клієнтів; зовнішні сервіси —

.env не читається; секрети не друкуються; команди розгортання не виконуються.
Розбіжність між постановкою, специфікацією і кодом — зупинка і запитання.

## Done when
- план погоджено до коду;
- кожен пункт мети — з тестами; тест архітектури забороняє імпорт між зрізами
  і імпорт адаптерів у ядро;
- тест-оракул читає docs/copy.md незалежно від застосунку і звіряє запасну сторінку;
```

Навіщо:

- **Модель і міграції одразу для всіх зрізів** — зрізи не чіпають міграцій і не конфліктують між собою.
- **Підключення зрізу без зміни спільних файлів** — два агенти паралельно працюють у різних теках і зливаються без конфліктів.
- **Порти і підставні реалізації** — тести не залежать від пошти, Telegram і мережі, тому швидкі й стабільні.
- **Маскування адрес із токеном** — посилання з токеном у журналі дорівнює ключу.
- **Europe/Kyiv замість фіксованого зсуву** — пастка з практики: між ефіром і першим заняттям відбувся перехід на зимовий час.
- **Тест архітектури** — межі перевіряє машина, а не домовленість.

### Картка 5. Реєстрація і лист

Найбільший зріз: з рецензією і перевіркою — близько двох годин. Його можна розділити на дві задачі — «реєстрація» і «лист».

```
## Goal
Відвідувач реєструється на сайті, отримує лист-запрошення і персональне посилання
в бота. Зріз лише додає свої файли.

## Context
Специфікація — docs/spec.md: маршрути зрізу, модель даних, налаштування.
Тексти — docs/copy.md: форма, екран успіху, лист, подія календаря, відписка;
згода — docs/legal/consent.md. Як підключається зріз і які є спільні порти —
CLAUDE.md, розділ «Зрізи».

## Що входить
1. Форма і POST /register — звичайний запит і htmx: перевірки на сервері,
   нормалізація адреси, однакова відповідь для нової і наявної адреси,
   перевірка Turnstile на сервері; обмеження частоти: 30 запитів на хвилину
   з однієї IP-адреси, 5 спроб на годину на адресу пошти.
2. Екран успіху за режимом сайту; кнопка бота з персональним токеном;
   без налаштованого бота — текст без кнопки.
3. Токени бота: одноразовий для екрана, окремий для листа; строк — сім діб;
   посилання https://t.me/ім'я_бота?start=токен.
4. Лист через Resend: HTML і текстова версії; надсилається у фоні після відповіді

   даних; ключ ідемпотентності; повтор після 429 і 5xx; один лист на учасника;
   заголовки List-Unsubscribe і List-Unsubscribe-Post.
5. Повторне надсилання листів зі збоєм — маршрут адміністратора за токеном.
6. Подія календаря .ics з VTIMEZONE для Europe/Kyiv, без фіксованих зсувів.
7. Відписка за підписаним токеном: сторінка, кнопка і відписка одним кліком;
   відписка видаляє дані учасника.
8. Подія generate_lead для аналітики — лише за згодою на cookie.

## Constraints
Лише файли зрізу за CLAUDE.md; потрібен новий пакет або зміна спільного файла —
зупинка і запитання. Тести не ходять у мережу: Resend, Turnstile і Telegram —
підставні реалізації; адреси лише на example.com.
Адреси, токени відписки і бота не потрапляють у журнали.
Тексти — дослівно з docs/copy.md і docs/legal/consent.md.
Обсяг — лише ця постановка: обробки команд бота, лічильників і експорту тут немає.

## Done when
- план погоджено до коду: перелік файлів, як перевіряється кожен пункт, запитання;
- тести написано першими, серед них: однакова відповідь для нової і наявної адреси;
  збій Resend — реєстрація успішна, лист у стані «збій»; повтор після 429;
  повторна реєстрація не дає другого листа; .ics з TZID; екран успіху з ботом і без;
- тест-оракул покриває форму, екран успіху, лист і відписку;
- uv run pytest, uv run ruff check ., uv run mypy src — зелені; CI зелений;
```

Навіщо:

- **Однакова відповідь для нової і наявної адреси** — форма не підказує стороннім, хто вже зареєстрований.

- **Ідемпотентність і один лист на учасника** — повтори мережі й подвійні натискання не дають дублів.
- **Turnstile на сервері** — ключ сайту публічний; захищає лише серверна перевірка.
- **Токени поза журналами** — посилання відписки і бота працюють як ключі.
- **Межі обсягу** — без них агент «заодно» починає писати бота.
- **Перелік тестів у критеріях** — найризиковіші випадки названо заздалегідь, а не залишено на розсуд агента.

Докладно: лекція 7 — тести першими; лекція 9 — пошук помилок.

### Картка 6. Бот

```
## Goal
Людина, яка зареєструвалась, натискає кнопку бота на екрані успіху або в листі.
Бот прив'язує її Telegram до реєстрації, перевіряє підписку на канал і видає
посилання на сторінку матеріалів. Непідписаному показує кнопку каналу
і кнопку повторної перевірки. Зріз лише додає свої файли.

## Context
Специфікація — docs/spec.md: правила команди /start, модель даних, налаштування бота.
Тексти — docs/copy.md: усі повідомлення і кнопки. Зріз «реєстрація і лист» уже
видає токени; імпортувати з нього не можна — спільне лише через фундамент (CLAUDE.md).

## Що входить
1. Вебхук POST /telegram/webhook: секрет у заголовку X-Telegram-Bot-Api-Secret-Token,
   порівняння зі сталим часом; неправильний секрет — 403 без обробки;
   лише особисті чати; без налаштувань бота маршрут відповідає 404, а сайт працює.
2. Реєстрація вебхука під час запуску — лише коли бот налаштований і адреса сайту
   починається з https://.
3. /start з токеном — правила в такому порядку: невідомий або прострочений токен;
   одноразовий токен уже використано; та сама прив'язка; нова прив'язка; конфлікт.
   Одночасні /start з одним токеном не дають двох прив'язок.
4. Перевірка підписки — getChatMember до каналу; збій Telegram — повідомлення
   «не вдалося перевірити» з кнопкою повтору; кнопка повтору прив'язок не створює.
5. Telegram Bot API — через HTTP-клієнт проєкту з тайм-аутами, без окремих бібліотек.

## Constraints
Лише файли зрізу; спільні файли не змінюються. Тести не ходять у мережу.
Токен бота є в адресі API — він не потрапляє в журнали; ідентифікатори й імена
Telegram — теж. .env не читається; команди розгортання не виконуються.

## Done when
- план погоджено до коду;
- тести першими: кожне правило /start, одночасні прив'язки, секрет вебхука,
  не особисті чати, статуси підписки і збій Telegram, 404 без налаштувань;
- тексти — з docs/copy.md, їх перевіряє тест-оракул;
- гейти зелені на окремій тестовій базі; CI зелений;
- підсумок: що змінено, коміти, гейти, розбіжності, відкриті запитання.
```

Навіщо:

- **Порядок правил `/start`** — без нього однакові випадки обробляються по-різному залежно від того, яку перевірку агент написав першою.
- **Секрет вебхука** — інакше «оновлення від Telegram» може надіслати будь-хто.
- **Одночасні `/start`** — двічі натиснута кнопка не має створити дві прив'язки.
- **404 без налаштувань** — сайт не залежить від бота: бот можна вимкнути, не зупиняючи реєстрацію.
- **Без окремих бібліотек** — менше залежностей, і поведінку видно в коді проєкту.

Зрізи «бот» і «лічильники й експорт» не перетинаються за файлами, тому їх пишуть два агенти паралельно — у двох робочих копіях git (worktree):

```
git fetch origin
git worktree add ../site-bot -b slice/bot origin/main
git worktree add ../site-extras -b slice/extras origin/main
```

- Кожна копія — зі своєю тестовою базою на окремому порту: спільна база зламає тести сусідньої сесії.
- Локальний файл правил дозволів агента (поза git) у нову копію не переноситься — його копіюють вручну. Інакше в новій теці агентові знову відкритий `.env`.
- Злиття: `git rebase origin/main`, гейти ще раз, push без force.

Докладно: лекція 10 — оркестр агентів.

### Картка 7. Лічильники й експорт

```
## Goal
Глядачі бачать на сайті два числа, що оновлюються самі: «зареєструвались»
і «підключили Telegram». Організатор за токеном отримує статистику і файл CSV
зі списком учасників. Зріз лише додає свої файли.

## Context
Специфікація — docs/spec.md: маршрути, модель даних. Підписи лічильників —
docs/copy.md. Як підключається зріз і як працює доступ адміністратора — CLAUDE.md.
Зріз «бот» пишеться паралельно; імпортувати з нього не можна.

## Що входить
1. Частина сторінки з двома числами і маршрут, що її віддає; оновлення кожні
   15 секунд засобами htmx; числа кешуються в пам'яті до 15 секунд;
   збій бази не ламає сторінку.
2. Статистика адміністратора — JSON: усього, за останню добу, листи зі збоєм,
   підключили Telegram, підписані на канал; збій бази — 503.
3. Експорт CSV: кодування, порядок стовпців і рядків, формат часу — за специфікацією;
   захист від формул у клітинках; без посилань відписки і службових ідентифікаторів.
4. Доступ — за токеном адміністратора; відповіді — без індексації і без кешування.

## Constraints
Лише файли зрізу; спільні файли не змінюються. Тести не ходять у мережу
і не спираються на відсутність зрізу «бот». У тестах лише адреси на example.com;
файл CSV ніде не зберігається і не друкується. .env не читається.

## Done when
- план погоджено до коду;
- тести першими: значення статистики; 401 без токена і з неправильним;
  CSV — порядок, формат, захист від формул, відсутність зайвих стовпців;
  кеш лічильників; сторінка з частиною лічильників і без неї;
- тест-оракул покриває підписи лічильників;
- гейти зелені на окремій тестовій базі; CI зелений;
- підсумок.
```

Навіщо:

- **Кеш на 15 секунд** — сотні глядачів, що оновлюють сторінку, не навантажують базу.
- **Захист від формул** — клітинка, що починається з `=`, у таблиці виконується як формула; це відома атака через CSV.
- **CSV не зберігається і не друкується** — у ньому персональні дані.
- **Незалежність від зрізу «бот»** — паралельні зрізи зливаються в будь-якому порядку.

Докладно: лекція 10.

### Картка 8. Лендінг

Два кроки: напрями макета в інструменті дизайну, потім агент збирає сторінку за обраним напрямом. Макет може зробити й сам агент — три статичні HTML-сторінки.

Крок 1 — напрями макета:

```
## Goal
Три візуальні напрями лендінгу вебінару за вкладеними brief.md, copy.md і consent.md.

## Context
У кожному напрямі, один під одним: перший екран, блок «Що в ефірі», лічильники,
блок форми реєстрації — тексти з відповідних розділів copy.md.
Значення у фігурних дужках підставляє сайт; для макета — реальна дата і час.
Текст згоди — з consent.md, повністю.

## Constraints
Мобільна версія першою: 375 пікселів без горизонтального прокручування.
Тексти — дослівно з файлів, нічого не дописувати.
Статичні HTML і CSS без фреймворків і зовнішніх залежностей; шрифти — системні.
Кольори — змінними CSS у :root (фон, текст, другорядний текст, акцент, лінії).
Контраст тексту — не нижче AA.

## Done when
Три помітно різні напрями; у кожного номер, коротка назва і одне речення про настрій.
```

Крок 2 — файли обраного напряму кладуться в теку `design/` репозиторію, далі нова сесія агента в режимі планування:

```
## Goal
Лендінг за обраним макетом: templates/landing.html і static/css/landing.css.

## Context
Макет — design/ (референс, не готовий код). Що дає сторінці маршрут / і як писати
landing.html — CLAUDE.md: тексти вже готові, частини форми і лічильників
підключаються за назвами.

## Constraints
Лише landing.html, landing.css і зображення макета в static/img/. Тексти не вписуються
вручну; умов режиму і дати в шаблоні немає. Палітра — змінними :root у landing.css;
класи частин форми і лічильників не переписуються.
375 пікселів без горизонтального прокручування.

## Done when
Тест-оракул текстів і гейти зелені: uv run pytest, uv run ruff check ., uv run mypy src.
```

Навіщо:

- **Три напрями** — вибір між варіантами швидший і точніший, ніж правки одного.
- **Кольори змінними `:root`** — форма і лічильники з інших зрізів перефарбовуються під макет без зміни їхніх файлів.
- **Макет — референс, не код** — HTML з інструменту дизайну не переноситься як є: сторінка будується на шаблонах проєкту.
- **Тексти не вписуються вручну** — інакше сторінка розходиться з `copy.md`, і тест-оракул це ловить.
- **375 пікселів** — більшість відвідувачів приходять із телефона.

Після злиття — перевірка на staging з телефона або у вузькому вікні: макет, форма, лічильники.

Докладно: лекція 5 — план до коду.

## 5. Гейти

Гейт — перевірка з відповіддю «так» або «ні», яку можна повторити. Агент запускає гейти сам, бо вони записані в критеріях готовності кожної постановки: у нього є об'єктивна умова завершення, а людина читає результат команд, а не слова «усе готово».

| Гейт | Що перевіряє | Як запускається |
| :-- | :-- | :-- |
| pytest | поведінку: кожен пункт постановки має тест | `uv run pytest` |
| ruff | помилки і підозрілі конструкції в коді | `uv run ruff check .` |
| mypy | типи | `uv run mypy src` |
| pre-commit | ті самі перевірки перед кожним комітом, плюс приватні ключі і конфлікти злиття | `uv run pre-commit install` один раз, далі само |
| CI | усе те саме на чистій машині з PostgreSQL на кожен push | GitHub Actions |
| тест-оракул | тексти сторінок дослівно збігаються з `docs/copy.md` | частина `pytest` |
| тест архітектури | межі: ядро без фреймворків, зрізи не імпортують один одного | частина `pytest` |

Мінімальний CI:

```
jobs:
  checks:
    runs-on: ubuntu-24.04
    services:
      postgres:
        image: postgres:17-alpine
        env:
          POSTGRES_USER: app
          POSTGRES_DB: app
          POSTGRES_HOST_AUTH_METHOD: trust
        ports:
          - 5432:5432
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
      - run: uv sync --dev --locked
      - run: uv run ruff check .
      - run: uv run mypy src
      - run: uv run pytest
        env:
          TEST_DATABASE_URL: postgresql://app@localhost:5432/app
```

**Тест-оракул текстів.** Окремий тест сам читає `docs/copy.md`, незалежно від застосунку, і перевіряє, що кожен текст є на відрендереній сторінці. Агент не може тихо «покращити» формулювання, а зміна текстів — це зміна документа, яку видно в рецензії.

**«Зелене або нічого»:**

- коміт — лише після того, як результат гейтів прочитано; коміт із червоним тестом не допускається;
- червоний тест не вимикається «тимчасово», а тести не редагуються, щоб пройти, — хіба що це прямо дозволяє задача;
- хостинг розгортає лише після зеленого CI: у Railway це налаштування «Wait for CI».

Чого гейти не бачать: зовнішні сервіси в тестах підставні. З практики: тести з підставним клієнтом не помітили, що справжній API відповідає помилкою на формат запиту; результат на сторінці не з'являвся без перезавантаження — тести, гейти і рев'ю-бот цього не побачили. Обидва випадки знайшла перевірка на staging. Гейти не замінюють огляду людиною.

Докладно: лекція 7 — тести першими; лекція 8 — гейти: зелене або нічого.

## 6. Рецензія в чистій сесії

Сесія, що писала код, «знає», що мала на увазі, і пропускає те саме вдруге. Чиста сесія бачить лише зміни і документи — як колега-рецензент.

Як запустити:

1. Після зелених гейтів — нова сесія агента в тій самій теці, без історії.
2. Постановка рецензії:

```
## Goal
Рецензія змін зрізу «назва зрізу»: знахідки, які треба виправити до злиття.

## Context
Зміни — git diff від коміту перед зрізом до HEAD. Постановка зрізу — файл постановки.
Специфікація — docs/spec.md, правила — CLAUDE.md.
Чек-лист — docs/templates/review-checklist.md.

## Constraints
Лише читання: код не змінюється. Знахідка — у форматі
файл:рядок — що не так — чому це проблема. Стиль і форматування не коментувати.

## Done when
Знахідки записано повним текстом у файл .handoff/review.md, від критичних до дрібних.
```

3. Людина вирішує щодо кожної знахідки: виправити, відкласти окремою задачею або відхилити з причиною. Критичні — безпека, втрата даних — виправляються до злиття без винятків.
4. Виправлення — новою постановкою авторові: файл знахідок разом із рішенням щодо кожної. Кожне виправлення — з тестом, який відтворює проблему.

Тека `.handoff/` — поза git: через неї сесії передають одна одній підсумки і знахідки.

Документи, від яких залежить код, — специфікація, вимоги, модель даних — рецензуються так само. Вбудовані команди рецензії в агентах — розділ 8.

Докладно: лекція 9 — полювання на баги; лекція 13 — рев'ю-бот у CI.

## 7. Розгортання

Два середовища на Railway — два окремі проєкти:

- **staging** (`app-next.example.com`) — розгортається сам після кожного зеленого CI на гілці `main`; тестовий бот, тестові ключі захисту форми, тестовий ресурс аналітики, сторінки закриті від індексації;
- **продакшн** (`app.example.com`) — розгортається рішенням людини, після перевірки на staging.

Налаштування вебсервісу:

| Налаштування | Значення |
| :-- | :-- |
| Джерело | репозиторій GitHub, гілка `main` |
| Wait for CI | увімкнено: без зеленого CI розгортання немає |
| Команда перед розгортанням | `alembic upgrade head` |
| Перевірка здоров'я | `/healthz` |
| Команда запуску | з `Procfile` |
| Змінні середовища | за `docs/env.example`; окремі значення для кожного середовища |

Розгортання після злиття займає близько п'яти хвилин: CI плюс збирання. У планах на ефір чи демонстрацію варто закладати саме стільки.

**Міграції лише додають.** Нові таблиці і стовпці, що допускають порожнє значення. Перейменування і видалення — пізніше, окремим релізом. Чому: попередня версія коду працює на новій схемі, тому відкат — це повторне розгортання попередньої версії без відкату бази.

**Відкат:** у панелі Railway — повторне розгортання попереднього успішного розгортання. База не відкочується, і завдяки правилу вище це безпечно.

**Хто що робить:**

- агент — код, тести, гейти, коміти; команд розгортання і змін змінних середовища він не виконує (правила проєкту і дозволи);
- людина — змінні середовища, домени, розгортання в продакшн і відкат.

Перед продакшном — перевірка на staging за списком: форма і лист, бот і сторінка матеріалів, лічильники, вигляд на телефоні.

Докладно: лекція 8 — CI як ворота перед злиттям.

## 8. Агент замінюваний — процес ні

Усе вище — процес: постановка, план, тести, гейти, рецензія. Інструменти відрізняються лише назвами. Правила проєкту варто писати один раз — у `AGENTS.md`, який читають усі три агенти.

Факти нижче звірено з офіційною документацією 20 жовтня 2026 року. Інструменти оновлюються щомісяця: назви команд варто звіряти з довідкою свого агента.

### Claude Code

- **Правила проєкту** — `CLAUDE.md` у корені репозиторію; `/init` створює стартовий файл, `/memory` відкриває його для правок. Якщо `CLAUDE.md` немає, Claude Code читає `AGENTS.md`. Якщо є обидва — у `CLAUDE.md` додається рядок `@AGENTS.md`, і спільні правила підключаються імпортом.
- **Режим планування** — `/plan` або `/plan опис задачі`.
- **Рецензія** — `/code-review` перевіряє поточний диф, гілку або pull request за номером; `/security-review` перевіряє зміни гілки на вразливості. Для чистої сесії — нова сесія агента.
- **Задачі в GitHub** — `/install-github-app` встановлює застосунок Claude і workflow GitHub Actions. З практики: агента кличуть згадкою `@claude` в Issue, а правки до його роботи пишуть коментарем у pull request, а не в Issue. Коментар в Issue запускає агента заново на новій гілці, без попереднього коду.
- **Хмарні сесії** — `/teleport` переносить хмарну сесію в термінал.

### Codex

- **Правила проєкту** — `AGENTS.md`: глобальний у `~/.codex/`, у корені репозиторію і у вкладених теках. Ближчий до робочої теки файл має пріоритет. `/init` створює стартовий `AGENTS.md`. Розмір усіх файлів правил разом — типово до 32 КіБ: правила мають бути короткими.
- **Режим планування** — `/plan` або Shift+Tab: агент збирає контекст, ставить уточнювальні запитання і складає план до коду.
- **Рецензія** — `/review`: проти базової гілки, незакомічених змін або окремого коміту, а також із власними інструкціями. Правила рецензії можна записати розділом `## Code Review Rules` в `AGENTS.md`.
- **Рецензія pull request у GitHub** — згадкою @Codex у pull request або автоматично для кожного.

### Antigravity

- **Правила проєкту** — `AGENTS.md` або `GEMINI.md` у теці проєкту, або окремі файли в `.agents/rules/`. Режими активації правил: завжди, за рішенням моделі (за описом правила), за масками файлів, вручну згадкою. Глобальні правила — `~/.gemini/AGENTS.md`.
- **Режим планування** — `/plan`: агент створює план реалізації до виконання; план і зміни можна коментувати.
- **Артефакти** — список задач, план реалізації, підсумок змін (walkthrough) — зручна основа для підсумку зрізу.
- **Рецензія** — окремої команди в документації не знайдено: нова розмова з постановкою рецензії з розділу 6.
- **Паралельна робота** — застосунок керує кількома локальними агентами одночасно і запускає заплановані задачі.

Докладно: лекція 3 — три агенти, один процес; лекція 4 — файли, які агент читає першими; лекція 12 — задача, яку агент виконує самостійно.
